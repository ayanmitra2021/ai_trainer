# Where You Should Be In The Loop

You said you want to write the key and complex parts yourself and let Claude Code handle the rest. This is the consolidated answer to "which parts are those" — the same flags appear inline in `project_plan.md` at the relevant step, so you don't have to cross-reference while you work. This is a judgment call, not a rule; treat it as a strong default.

The pattern across all eleven: **it's almost never "write the Python yourself" — it's "own the prompt file, the rubric, or the policy decision."** Claude Code can write the plumbing around any of these perfectly well. What it can't do is make the judgment call that the plumbing serves.

| Step | What to own | Why it's not a delegation task |
|---|---|---|
| 0.4 Agent framework | Review/tune the base `Agent` class design — retry behavior, how structured-output validation failures are handled, what "success" means in `agent_runs` | Every one of the other nine agents inherits this contract — get it wrong and the mistake propagates nine times over. It's also exactly the kind of foundational decision that's genuinely interesting to make yourself rather than delegate. |
| 1.2 Usage-Signal MCP adapter | Decide what actually counts as a meaningful usage signal, and how a Claude Code session or a commit maps to a skill node | This is a modeling judgment, not an engineering one — get it wrong and Adoption Pulse either misses real adoption or flags noise as signal. No amount of clean code fixes a bad mapping rule. |
| 2.3 Certification Advisor | The targeted-question set itself, and the recommendation logic for when the answers don't cleanly point to one certification | A bad recommendation costs someone a real exam fee (often $100–300) and weeks of prep aimed at the wrong credential. Which four questions to ask, and how to weigh a case like "wants Anthropic, wants to architect systems, has zero technical background," are judgment calls — not a filter query with one obvious answer. |
| 2.6 Item-Writer prompt | The trap-reveal mechanic itself — what makes a good trap, and what the reveal copy says | This is your signature pedagogical device from the CCAF materials. It's also the single most "you" part of this product; delegating the prompt that defines it would hollow out the one thing that makes Mastery Mesh distinctive. |
| 2.7 Grader rubric | The rubric for free-text grading, especially partial-credit logic | Grading rubrics encode what you actually value in an answer. Get this wrong and every downstream skill score is measuring the wrong thing, quietly. |
| 3.2 Correlation Agent | The correlation methodology and the "correlation, not causation" framing in its own output | This is the ethically load-bearing agent in the whole system — it's the one that decides someone looks like they're not adopting what they learned. Worth designing carefully rather than trusting a first-draft prompt. |
| 3.3 Nudge Composer prompt | Tone and wording of anything a real practitioner will read about themselves | Nudges land in someone's inbox. A tone-deaf nudge (or a technically-accurate-but-demoralizing one) does real damage to how this tool is received internally — worth more scrutiny than any other copy in the product. |
| 3.4 Rollup Reporter | The minimum-cohort-size policy before a rollup is shown to leadership | This is a privacy decision with a number attached (`rollups.min_cohort_size_met`). Pick the number deliberately; don't let a default slip in. |
| 4.4 Quiz Runner (trap-reveal UI) | The interaction/animation at the moment of reveal | The mechanic's *effect* on the practitioner lives as much in the UI beat as in the copy. Worth a personal design pass once the plumbing works. |
| 5.2 Auth & access control | ~~Who can see individual-level data vs. only aggregates, before any real usage~~ **Policy decided.** Two roles: practitioner (session cookie, no password — email + name + org level on landing page) and admin/leadership (bcrypt password, forced change from "welcome" on first login). See `docs/architecture.md` §Auth & sessions for the full design. Implementation is mechanical from here. | ~~Get this wrong before real practitioners are in the system and it's a trust problem, not a bug report.~~ Already decided — Claude Code can implement without further input. |
| 7.2 Nudge Category Generator prompt | The criteria boundaries that define a "category" of practitioners worth nudging, the `tone_hint` vocabulary each category carries, and the system prompt's framing of what categories are appropriate vs. off-limits | This prompt determines who ever gets nudged and with what tone. A category that flags ordinary behavior (e.g. "practitioners who skip weekends") or a `tone_hint` that implies urgency or failure will erode trust across the whole team — possibly permanently. The LLM never sees individual practitioner data, but the categories it generates shape every campaign message that does. Worth designing the prompt carefully before the first implementation, not after the first complaint. |
| 8.1 Model abstraction layer | Decide the provider-agnostic interface and confirm it covers all agent needs without leaking Anthropic specifics | The `ModelClient` protocol is the seam between agents and providers. Get it wrong and every agent inherits the leak — e.g., if the protocol assumes Anthropic's `messages.parse()` shape, NVIDIA can't implement it cleanly. This is the one architectural decision that affects all 9 agents. |
| 10.1 Certification domain seed data 👤 | Validate the bootstrap domain rows in `backend/seed/certification_domains.py` against the official exam guide PDF for each certification — weights, domain names, and descriptions — before the first production use | Domain data that doesn't match the real exam objectives will cause the Item-Writer to generate questions for the wrong topics, and practitioners will build false confidence for an exam they're not actually preparing for. Use the official exam guide PDFs (most providers publish these free), not third-party study guides. **Ongoing freshness is handled from Step 10.3 onward** by the Cert Domain Discovery Agent — the Step 10.1 seed is the one-time bootstrap only. |
| 10.3 Cert Domain Discovery Agent prompt 👤 | Write `agents/prompts/cert_domain_discovery.md` yourself — specifically the confidence-signaling vocabulary, the instructions for what to say when the agent is uncertain, and what evidence level qualifies as "high confidence" | This agent's approved output replaces the exam domain data all practitioners are tested against. A prompt that fabricates plausible-sounding but incorrect domain names with high confidence is more dangerous than one that says "I cannot find a reliable source" — at least a refusal is visible to the reviewing admin. Own the confidence-level distinctions (high / medium / low), the rule that the agent must flag uncertainty rather than fill gaps from imagination, and the instruction for certs it has no training data for. Review at least the first few live proposals before trusting outputs at scale. |
| 10.3 Item-Writer `is_cert_evaluated` judgment | Review and finalize the prompt logic that decides whether an item is directly tested in the cert exam (`is_cert_evaluated = true`) vs. supplementary (`false`) | This boundary determines whether a correct answer improves the practitioner's exam-domain readiness score. A prompt that tags too many items as `is_cert_evaluated` inflates readiness scores; too few means the chart never moves. The judgment of "does this appear in the exam blueprint?" is pedagogical, not algorithmic. |
| 13.2 CertSkillMapperAgent prompt | Write `agents/prompts/cert_skill_mapper.md` yourself — specifically the confidence-signaling vocabulary (`high` / `medium` / `low`), the rule for when fewer than 10 skills are acceptable, what qualifies as "official" vs. third-party evidence, and the failure-mode instructions when the exam guide cannot be found | This prompt's output becomes the skill set every practitioner targeting this cert trains against. A prompt that confidently invents plausible-sounding skills when the exam guide isn't findable is more dangerous than one that honestly says "I found partial evidence." Own the confidence thresholds, the "name skills at the right granularity" rule, and the instruction to flag uncertainty explicitly rather than fill gaps with imagination. Review at least the first live CCAR-P discovery run against the official Anthropic exam guide before trusting outputs at scale. |
| 18.2 ByteSizedLessonAgent prompt | Write `agents/prompts/byte_sized_lesson.md` yourself — specifically the engagement style instructions (conversational tone, emoji policy, hook structure, sign-off line), the "Common pitfalls 🪤" guidance (what makes a pitfall genuinely insightful vs. generic), the "Quick check ✅" question style, and the link-quality rules | Byte-Sized Learning is the practitioner's primary post-quiz "what do I do with this gap" touchpoint. A bland, corporate, or jargon-heavy write-up will be skipped; an engaging, honest, specific one becomes a genuinely useful study companion. The engagement quality lives in the prompt's instructions — Claude Code can write the agent plumbing, but you need to decide what "fun and useful" looks like in practice. Also own the link-quality rules: what counts as a reputable source, how to handle topics where the official docs are dry or sparse, and whether YouTube links are acceptable for all cert topics or only some. Read at least 3–5 generated samples before going live. |

## What this deliberately doesn't include

Anything CRUD, any API route, any migration, any frontend layout, any test scaffolding, the MCP server plumbing itself (as opposed to the signal-mapping judgment inside it), and the orchestration workflows (their logic is "call these agents in this order," which is a sequencing decision the plan already makes for you). Claude Code should own all of that outright — flagging it here too would just dilute the list down to the same ten things that actually need you.
